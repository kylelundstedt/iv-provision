Version history for the provisioning recipe. Moved off the landing page
2026-09-15 — a changelog this long is a reference, not an introduction.

## Versioning

Versioning is via **Git tags of this provisioning repo**, not
`iv-image:MAJOR.MINOR.PATCH` Docker image tags. Pin a recipe by checking out a
tag/sha before running `provision-iv.sh`.

### Provisioning-era releases

| Version | Change |
| ------- | ------ |
| `3.0.24` | **Doc-site restructure, and `entire-push-check` says why it failed.** The site had no landing page: `index.qmd` carried the design rationale, the file layout *and* the full release history, so the first page a reader met never said what the repo or the host were — while `iv-provision` had quietly become the control-plane host that also runs a scheduled fleet check. Split into `index.qmd` (landing: what the **host** does, what the **repo** is, where to go next), `design.md` and `releases.md`, with 137 lines moved verbatim — the 2026-08-18 Shelley retraction is a correction record and was not paraphrased. Adds `retiring.md` to the site, which existed in the repo but was never rendered despite dotfiles citing it as the runbook for the one unrecoverable fleet operation. Verified by rendering in a scratch clone on the VM: nine pages, links rewritten, live site untouched. Corrected in passing — the include list does **not** set nav order (it sorts alphabetically by filename), so reading order lives in the landing page's table. `bin/entire-push-check` now keeps ssh's stderr instead of discarding it: three weeks of failures on the mini all read "integration and ssh both failed" while the cause was that the mini's exe.dev key is served by the 1Password agent, which auto-locks after 60 minutes, so every scheduled run found no identity and every success in its history was an interactive run. It now names auth-vs-connect causes and reports anything else verbatim. The check itself has since moved to run **on this VM** (dotfiles #51), where the http-proxy integration supplies the inventory with no SSH key at all — placement rule in dotfiles `agent_docs/service-placement.md`. Vendored skills were deliberately **not** refreshed: `vendor-skills.sh` reports upstream drift of 54 files / 568+641 lines including six `.ts` artifacts and two new skills, which `building.md` says wants real review rather than riding along in a release. |
| `3.0.23` | **AgentsView over exe.dev peer integrations.** The source daemon binds loopback behind the VM's own exe.dev auth proxy instead of the tailnet, and the sync token becomes a public fleet constant (`AGENTSVIEW_FLEET_TOKEN`): the peer integration is the access control, the token only satisfies AgentsView's handshake. `create-vm` now enrolls the VM it makes by creating its `av-src-<name>` peer integration (its token widened to `integrations add`), and the collector on `iv-agentsview` reconciles its fan-in from that list daily -- closing the gap that left three VMs created 2026-08-29..09-03 uncollected after the manual step was retired. `retiring.md` step 2 is now one lobby command. Canary and design: dotfiles `agent_docs/agentsview-peer-path.md`. |
| `3.0.22` | Vendors **Tailscale's own agent skill** (`tailscale/tailscale-skill`, alpha) as a team row. The tailnet is a provisioning concern here -- every VM joins in `provision-iv.sh` -- and the failures are Tailscale-shaped: on 2026-08-23 a `tag:dev` mint failed with `requested tags [tag:dev] are invalid or not permitted` and the OAuth scope was re-verified twice before the answer turned out to be tag *ownership*. Nothing on the VM carried that material. Deliberately **not** Tailscale's remote MCP server (`tailscale.mcp.kapa.ai`): probed, it is doc search behind per-client browser OAuth, so it would be the fleet's first MCP server needing a human at a browser per VM -- against the property every `mcp.manifest` row has, that the credential lives at the exe.dev edge and a recreated VM works unattended. The skill teaches upstream's `tailscale up --auth-key=<console key>` join, which is what `tailnet.md` exists to prevent, so both `tailnet.md` and `join-tailnet` now record the boundary and which file wins. Also backfills the `3.0.20` and `3.0.21` rows this table never got. |
| `3.0.21` | Docs-only. Carries the `api-exe-new` scope table correction from #45 into a tag: the fleet reads skills from a detached checkout, so a correction on `main` is invisible until a release names it, and a VM created at `3.0.20` still shipped the stale table. Bumps `create-vm`'s four self-pins on the release branch so tag and pin are the same commit. |
| `3.0.20` | `create-vm` pins the base image carrying the **`.bashrc` PATH fix** (`exeslim-dev` `2026-08-28.24.1`). Upstream appended the `~/.local/bin` export below Ubuntu skel's `case $- in *i*) ;; *) return;; esac`, making it dead code for every non-interactive shell -- so `ssh <vm> '<cmd>'` could not find `python3` on a VM where it was installed and worked interactively. Verified in the image bytes, not assumed: both builds pulled and the failing case run against each. The bug hid for months because the older base shipped zsh, whose `.zshenv` is read on every invocation. |
| `3.0.19` | `create-vm` pins **itself**. `3.0.17` and `3.0.18` were each tagged *before* the pin bump that followed them, so a VM created at either tag provisioned one release behind the tag it was created from — a skill telling you to pin, at a pin that is stale by construction. Fixed by bumping the pin and cutting the tag on the same commit, which is what the pin has to mean if "always pin the tag" is to hold. No provisioning change. |
| `3.0.18` | **`create-repo`**: create a GitHub repo and seed it with files from a VM, with no laptop, no `gh` login and no token — the counterpart to `create-vm`, through the `mcp-github-home` integration whose credential stays at the exe.dev edge. Ships two executables beside the prose (`gh-mcp.sh`, `push-tree.sh`) because streamable-HTTP MCP is three round trips and returns its session id in a header. The trap it exists to document: a repo created this way has **no `repo-*` integration**, so `git clone` of a new private repo answers `Repository not found` and a push to a new public one is `integration is read-only` — neither is a broken repo, and the MCP path is the write path until the owner mints the integration. Records the two hard limits found by probing: there is no delete-repository tool at all, and org repos are refused by SAML SSO. Smoke now asserts the scripts arrive executable, which `cp -a` preserves only if the mode was committed. |
| `3.0.17` | Smoke: check the `aws` pin where it actually lives. |
| `3.0.16` | Doc-only: base recreate playbook and migration progress in `TODO.md`. |
| `3.0.15` | **Entire CLI `0.8.42` → `0.10.1`** (checksum-verified), after re-qualifying plugin `entire-agent-shelley` `0.1.3` against it on the dedicated `iv-entire-agent-shelley` VM — the full live suite (`test-shelley-live.sh`, including real checkpoint condensation and the `entire/checkpoints/v1` ref) passed; `0.10.0` passed identically, so the newer stable was pinned. The jump skips `0.9.x`, which is why re-qualification rather than a bare version edit was the gate; the plugin is unchanged. Also doc-only: the tailnet credential **has been narrowed** to `auth_keys` on `tag:dev` (2026-08-19), so `tailnet.md` records deployed state rather than a proposal — a tagged VM can join or rejoin unattended and can do nothing else (enumerating the tailnet, reading or deleting any node, the policy file and DNS all return 403, verified after the change). Adds the console procedure that matches the UI (a Read/Write grid under **Keys → Auth Keys**, not the API-doc scope names), where the credential goes in exe.dev (`api-tailscale` → Authentication → basic auth), and why the old client is revoked last: whether `preauthorized: true` falls inside Auth Keys Write is undocumented — it does. |
| `3.0.14` | Warn instead of failing silently when the tailnet credential cannot list devices. Stale-node cleanup — the only part of provisioning needing `devices:core` rather than just `auth_keys` — would otherwise 403, yield nothing, skip its loop, and let the VM join as `<hostname>-1` with no message anywhere. Documents how to narrow the grant **without** building a broker: Tailscale's OAuth scopes already bind key-minting to named tags (minting `tag:iv-aperture-admin` is refused) and already deny the policy file and DNS, so dropping `devices:core` is a console change rather than a service to operate — with the `-1` collision as its stated cost. |
| `3.0.13` | Doc-only. `api-tailscale` now attaches through a dedicated **`tailnet`** exe.dev tag rather than per VM, so a recreated VM rejoins unattended instead of being inert until a human attaches the integration — a hole that could only be closed from a workstation, since a VM off the tailnet is unreachable from other VMs. Deliberately *not* `tag:iv`: that tag already carries the MCP integrations, and folding key-minting into it would be the same widening `auto:all` was rejected for, disguised as reuse. A tag named for the capability also reads correctly at the moment someone applies it. |
| `3.0.12` | Doc-only. Corrects `3.0.11`'s claim that the exe.dev tag `iv` was "unused for attachment" — it already carries `api-motherduck-mcp` and `api-github-copilot-home`, which makes the `tag:iv` proposal one more attachment onto a working mechanism rather than a new pattern. The claim was inferred from inside a VM, where `reflection` reports a VM's own tags and integrations but never the attachment *rules*; effects are visible there, rules are not. Records the resulting standing rule: control-plane facts are confirmed off-VM via `ssh exe.dev integrations`. |
| `3.0.11` | Doc-only. Tell the **two tag systems** apart: Tailscale tags (`tag:dev`) govern reachability and the SSH policy; exe.dev VM tags (`iv`, `mcp-agent`) govern which integrations attach. exe.dev's attach syntax borrows Tailscale's `tag:` prefix, which produced two successive errors in `tailnet.md` — the second while correcting the first — so the distinction is now a table. Settles that Tailscale `tag:dev` needs no fleet decision (`provision-iv.sh` hardcodes it into every join key) and records why `auto:all` is the wrong attachment for `api-tailscale`: it would cover every future VM, including sandboxes, discarding the consent signal the design rests on. Proposes `tag:iv` instead, so a recreated VM rejoins unattended. |
| `3.0.10` | Doc-only. Ships the corrected "Authoring boundary" (single writer, restored 2026-08-19), the PR-from-a-VM procedure and the fork base-branch trap, and the refreshed `TODO.md` — all of which merged to `main` *after* `3.0.9` was tagged, so every fleet VM's checkout still showed the superseded "any host may author" text. A VM's `~/iv-provision` sits detached at a release tag, so documentation only reaches the fleet when a tag moves; a doc fix that is not tagged is a doc fix the fleet cannot read. |
| `3.0.9` | CI: build a branch on `push` only for `main`, so a PR stops running the identical commit twice — the duplicate run for `969c66a` hung six hours in Shellcheck and failed the PR while the `pull_request` run for the same tree passed in sixteen seconds. Install shellcheck from a pinned, checksum-verified release instead of `apt-get update && apt-get install`, which was the step that hung and left the linter version floating; add `cancel-in-progress` concurrency and a 10-minute job timeout so a wedged run fails fast rather than at the 6-hour limit. Probe the `claude`/`codex` **floors** across every copy on `PATH`, not just `~/.local/bin`. The pre-exeslim `exe` base ships them in `/usr/local/bin`, where the probe could not see them, so the floor never applied and provisioning *downgraded* working agents (kgl-songs: Claude Code 2.1.222 → 2.1.220, Codex 0.146.1 → 0.146.0) while stranding ~290 MB of shadowed duplicate — the exact waste `install_claude_code` exists to avoid. Also key the generated ssh block on tailnet **membership** (`Match exec "tailscale ip -4 %h"`) instead of the `iv-*` name prefix, which never matched `kgl-songs`, `kgl-thoughts` or `telnyx-vm`; and reconcile that block on every provision rather than appending it once, so a wrong stanza can be corrected on VMs that already have one. |
| `3.0.8` | Generate the per-host AgentsView token during provisioning instead of requiring a hand-invented one. It is a self-chosen random secret, so a human typing it added nothing but a manual step that blocked unattended bring-up. Minted once, never rotated (the collector stores it), still per host. |
| `3.0.7` | Fix `local` used outside a function in the AgentsView `auth_token` block, which aborted provisioning on the first VM to have a `source.env`. `bash -n` accepts it; shellcheck (SC2168) does not, so it now runs in the tests and in CI over every shell file. |
| `3.0.6` | Identify Shelley by systemd's `MainPID`, not by process name. `KillMode=process` lets terminal helpers outlive a restart, and they are named `shelley` too — so the 3.0.4 "is the override live?" check read a surviving helper's environment and restarted Shelley on **every** run, and the swap's wait-for-exit loop never broke. |
| `3.0.5` | **Provisioning joins the tailnet again.** Moving the tailscale install into the provisioner without the join had silently replaced a one-command bring-up with a hand-run OAuth dance. The join is gated on the `api-tailscale` integration being attached — the attachment is the consent signal, so nothing is baked in and no credential reaches the VM. Also corrects the docs: there is no `iv` tag, and the integration is normally attached to nothing by design. |
| `3.0.4` | Stop restarting Shelley on every re-provision. The no-change path restarted unconditionally to make the self-update drop-in take effect, killing every in-flight conversation on the VM — including, during a fleet refresh, the one driving it. Now restarts only when the override is not already live in the running process (`/proc/<pid>/environ`). |
| `3.0.3` | Treat the `claude`/`codex` pins as **floors**: an exact match downgraded a self-updated agent (2.1.235 → 2.1.220) and would have done so on every VM in a fleet refresh. Announce the provisioning revision up front and warn when the checkout is behind its upstream or dirty — a stale local `main` had silently re-provisioned an older recipe. |
| `3.0.2` | Install a uv-managed `python3`: without it `entire-agent-shelley` cannot run, so the ACR capture path was dead while Shelley's hooks still exited 0. Rebuild the smoke suite's long-line fixture in awk so a missing interpreter cannot abort the whole suite at line 42. Ship the `herdr` skill, which `.gitignore` had withheld from every VM despite `skills.manifest` asking for it. Prefer this over `3.0.1`. |
| `3.0.1` | Merge `~/.claude/settings.json` instead of overwriting it, so a personal overlay's `SessionStart` hook survives provisioning; fix the Shelley socket-activation race for real (documented as fixed in a `2.9.1` that was never tagged) and health-check the *serving* version, not just the binary on disk; install Claude Code into its native versioned layout. |
| `3.0.0` | **Renamed `iv-image` → `iv-provision`.** The provisioner now owns everything a fleet VM needs, ending the dependency on the personal dotfiles repo: `tailscale` (with `--ssh`; a fresh VM previously could not join the tailnet at all), `uv`, `claude`, `codex`, the Entire CLI + `entire-agent-shelley` plugin + vendored `entire-agent-agentsview` (ADR 0010's primary ACR capture path, which did not survive a recreate), and the `provisioning/` manifests (retiring `dotfiles-manifest.pin`). Fixes AgentsView's CLI, locked out by its own `--require-auth`, and rotates its unbounded debug log. (The socket race and settings-merge fixes landed in `3.0.1` — prefer it.) Documents the real base image (`ghcr.io/kylelundstedt/exeslim-dev`) and retracts the "custom images disable Shelley" claim. Skills refreshed. Breaking: new repo name, new clone URL, `exeuntu_image_revision` → `base_image_*` in the lock file. |
| `2.9.1` | `install_shelley`: stop the socket before the service, closing the race where socket activation restarted the old binary and let it self-upgrade over the pin. |
| `2.9.0` | Pin the subscription-capable `aifoundry-org/shelley` release and disable Shelley's unmanaged self-update; tests tolerate optional provisioned tools. |
| `2.8.0` | `tigris` 3.1.0 → 3.6.1 (adds `TIGRIS_FORCE_PATH_STYLE`). |
